# Chapter 8: On-Call

## Core Idea
On-call is sustainable only when pager load is bounded, rotations are staffed appropriately, and alerts are actionable. This chapter provides concrete implementation patterns for small and large teams.

## Frameworks Introduced
- **Anatomy of pager load**:
  - Alert volume: raw number of pages per shift
  - Alert quality: % of alerts that are actionable (require actual response)
  - Context switches: interruptions that prevent deep work
  - Follow-on work: tickets, fixes, and postmortems generated by incidents
  - Escalation frequency: how often on-call must escalate to others

- **Healthy on-call checklist**:
  - Max 2 significant events per on-call shift (Google target)
  - Each event should be resolvable by the on-caller alone or with one escalation
  - Runbooks must exist and be accurate for every alert that fires
  - Post-event review for every on-call shift (even a 5-minute review catches drift)

## Key Concepts
- **On-call rotation size**: ~8 engineers minimum for sustainable follow-the-sun (3 shifts × 8h); smaller rotations cause burnout and alert fatigue.
- **Handoff protocol**: explicit handoff at shift boundary; IC transfers context; in-flight incidents documented.
- **Operational underload**: rotation so large that engineers lose system context between shifts; counteract with more risk-taking (faster releases, DR testing).
- **Developer on-call**: developers in rotation gain production intuition; SREs should not be the only ones on-call for a product.

## On-Call Team Dynamics
- Establish clear escalation paths before going live; no improvising under pressure.
- On-call engineers need real authority to make production changes; bureaucratic approval during incidents wastes error budget.
- Multi-site rotations: hand off at the start of business in the next timezone; never hand off in the middle of an active incident without explicit IC handoff.

## Worked Example: Small Team (Evernote)
- Fewer than 8 engineers; solved with "follow-the-sun" by bringing developers into rotation.
- Trade-off: developers on-call interrupt feature work; mitigated by limiting developer exposure to their own services.
- Key insight: a mixed SRE/developer rotation improves developer accountability for production quality.

## Worked Example: New Google Team
- Bootstrapping a new SRE team: first on-call rotations are understaffed by design; explicit "learning phase" with escalation to senior SREs.
- Runbook creation sprint before first on-call duty — if no runbook, alert should be suppressed or changed to ticket.

## Reference Table: On-Call Flexibility Options

| Pattern | When to use | Trade-off |
|---------|-------------|-----------|
| Follow-the-sun | Large team, multiple time zones | Requires explicit handoffs |
| Pooled rotation | Small team, all same TZ | Can cause burnout without strong alert hygiene |
| Developer-in-rotation | Few SREs, new service | Disrupts feature work; improves code quality |
| Tiered on-call | Multiple criticality levels | Complexity in escalation paths |

## Anti-patterns
- **Alert fatigue from low-quality alerts**: alerts that don't require action train on-callers to ignore them.
- **No runbooks**: undocumented alerts produce inconsistent responses and longer MTTR.
- **Heroics as success**: incident requiring off-hours developer heroics is a process failure, not a win.
- **Skipping shift handoff reviews**: drift in system state goes undetected until it becomes an outage.

## Key Takeaways
1. Target ≤2 significant events per on-call shift; more indicates alert quality problems.
2. All alerts must have runbooks; no runbook = no alert (or ticket-only).
3. On-call requires real production authority; approval chains during incidents are dangerous.
4. Bring developers into on-call rotation for their own services — it improves code reliability and reduces SRE toil.
